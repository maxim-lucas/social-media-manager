# Posting order — read this before building or rebuilding any tray

Every tray directory (`01-how-it-works` … `10-feedback`) now contains a second,
redundant copy of its own content, prefixed `00-`, `01-`, `02-`… in **exact
posting order**. Nothing was renamed or deleted — the original
`priceback-hl-<id>-NN-en/fr.png` files (and, for the five trays filled from
`04-community`, the source files there) stay put and stay what the render and
verify scripts read. The numbered copies exist so that opening one folder on
GitHub shows the whole story, in order, without cross-referencing five other
folders or a table in a doc.

```
00-guard-en-fr-will-follow.png   ← posted FIRST. Bilingual: says "the French follows" in a way
                                    that reads even if you don't read the words (see below)
01-en-*  02-en-*  03-en-* …      ← the English frames, in this order, nothing else between them
NN-guard-fr-starts-here.png      ← posted immediately after the last English frame
NN-fr-*  NN-fr-* …               ← the French frames, in the SAME order as their English pairs
```

This is the one structural rule for every Highlight: **guard → English → guard →
French**, and it is not a preference — it is downstream of two real Instagram
limitations.

---

## Why this order, specifically

**1. Highlights cannot be built through the Graph API — phone only, one story at
a time, selected from the archive.** `scripts/publish-due.js` (this repo's
publisher) posts Stories; it cannot create or edit a Highlight. So the sequence
below has to survive a manual step no script controls, which means it has to be
*simple enough that the person doing it by hand cannot get it wrong* — one
reason the guard frames say what they say instead of relying on a caption
somebody might skip.

**2. When you build a Highlight from several archived Stories at once, Instagram
keeps the order you tap them in** — it does not silently re-sort by original
post time. That is what makes this whole scheme reliable: post the four
sections **in this order, in one sitting**, and selecting them **in the same
order** when you build the tray reproduces it exactly. (Instagram also lets you
drag to reorder an existing Highlight afterward, in the tray's edit view — that
is the fallback if a tray is ever built out of order, not the primary method;
fixing it by hand once a tray is live is real work, so get the tap order right
the first time.)

**Neither of those is a reason to skip the redundant copies below.** They exist
so a human can *verify* the order was right before or after building the tray,
by scrolling one folder — not by re-deriving it from `strings.json` and a
memory of which community story filled which tray.

---

## The rule this replaces

The pack was built assuming the two guard frames only needed to exist **once**,
reused by reference from `04-community/00-language-notice/` across all ten
trays (still true — see `HIGHLIGHTS.md` and `NOTES.md`). That is still how the
frames get *posted* to the Instagram archive: post the intro and the FR card a
single time, then pull the same two archived stories into every tray you build.
What changed is that a shared-by-reference asset is invisible on a GitHub file
listing — you cannot tell, from `06-tips/`, that a guard frame belongs at
position 0 and another at position 5 unless you already know to go look in
`00-language-notice/`. The numbered copies in every tray folder close that gap:
the repo now shows the same thing the phone will show, in the same folder.

**One highlight, one sitting, one concept.** Never mix frames from two trays (or
two unrelated stories) into the same posting session — a batch of unrelated
images posted together has no argument, and Instagram's own audience metrics
read a mixed batch as noise. If a tray does not fit in one sitting, that is a
sign it is two trays, not a scheduling problem.

**If a future pack's guard design does not match its own art** (different
palette, different frame system than `04-community`'s), do not reuse the
`04-community` guard as-is — render a new intro / FR-card pair in that pack's
own scene file, built off the same underlying kit (`sm-content/brand/`) so it
reads as one system rather than a signpost that visibly belongs to a different
account. Every pack so far imports the same `brand/palette.js`, `brand/type.js`
and `brand/ig.js`, which is why one shared guard has been correct until now —
check that before assuming it still is, the next time a pack's `tokens.js`
diverges.

## Rebuilding a tray after `facts.json` or copy changes

The numbered copies are **not** regenerated by `scenes/render.js` — they are a
snapshot for humans, not a build artifact. After any re-render:

```bash
node sm-content/05-highlights/scenes/build-strings.js
node sm-content/05-highlights/scenes/render.js
node sm-content/05-highlights/scenes/verify.js
```

then re-copy the changed tray's numbered files by hand (or diff the folder —
the numbered copies are byte-identical to their source, so `git diff --stat`
against the previous commit shows exactly which ones drifted).
